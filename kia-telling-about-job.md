## 1. Краткий профессиональный профиль

Я Frontend Developer с коммерческим опытом работы в Uplab с августа 2023 по сентябрь 2026 года. Работал над корпоративным сайтом и сайтом вакансий Корпорации СТС. Основной стек — Vue 3, Nuxt 3, TypeScript и JavaScript.

Моя работа включала разработку пользовательских интерфейсов, интеграцию с API, формы и авторизацию, поиск с автодополнением, фильтрацию и пагинацию вакансий, управление состоянием, адаптивную вёрстку и обработку асинхронных состояний. Взаимодействовал с backend-разработчиками, дизайнерами, QA, менеджерами и другими участниками команды.

По мере работы росла самостоятельность: от реализации отдельных задач с обратной связью до самостоятельного ведения frontend-функциональности в своей зоне ответственности, обсуждения API-контрактов и технических решений, прохождения Code Review и сопровождения задач до проверки QA.

Ориентир дальнейшего поиска — позиции Middle Frontend Developer. Это целевой уровень вакансий и оценка фактической зрелости навыков к позднему этапу работы, а не официально присвоенный грейд в Uplab.

## 6. Основные проекты и технические кейсы

### 6.1. Поиск вакансий с автодополнением

**Пользовательская задача:** быстро найти вакансию по названию должности, не просматривая весь список вручную.

**Поведение интерфейса:**
- Поиск по названию вакансии.
- Подсказки появляются после ввода минимум двух символов.
- Между вводом символов и запросом используется debounce около 300 мс.
- Подсказки отображаются под полем.
- Предусмотрен выбор мышью и клавиатурой.
- Очистка поля закрывает подсказки и возвращает общий список с учётом активных фильтров.
- Есть состояния загрузки, пустого результата и ошибки.

**Моя зона ответственности:** реализация frontend-поиска и автодополнения, debounce, интеграция с API, обработка состояния подсказок и защита от отображения устаревших результатов.

**Техническое описание согласованного решения:**
1. Пользователь вводит текст.
2. После минимальной длины строки запускается debounce.
3. По окончании задержки выполняется запрос за подсказками.
4. При изменении строки предыдущий запрос отменяется через AbortController.
5. Дополнительно проверяется актуальность поисковой строки, чтобы более старый ответ не перезаписал результат для нового значения.
6. UI показывает актуальные подсказки и соответствующее состояние.

**Требует уточнения:** точный API endpoint, структура ответа, точные имена composable/component/service, реализация обработки AbortError и то, где именно создавался AbortController.

**Технические темы для дальнейшей подготовки:** debounce и throttle; Promise; AbortController и AbortSignal; отмена запроса; race conditions; устаревшие ответы; обработка ошибок и повторный запрос.

### 6.2. Серверная фильтрация и пагинация вакансий

**Пользовательская задача:** сузить список вакансий по параметрам и удобно переходить между страницами результатов.

**Фильтры:**
- подразделение / направление;
- регион;
- тип занятости.

В каждом фильтре выбиралось одно значение; значения разных фильтров можно было комбинировать. Фильтры применялись после выбора. Предусматривался сброс отдельного фильтра и общий сброс.

**Согласованное техническое решение:**
- Фильтрация выполнялась на сервере: frontend передавал параметры, backend возвращал подходящий список.
- Состояние фильтров находилось в локальном состоянии страницы / composable, а не в глобальном Pinia store.
- Параметры синхронизировались с URL.
- При изменении фильтров текущая страница сбрасывалась на первую.
- Использовалась серверная пагинация: `page` и `limit`.
- Размер страницы — 10 вакансий.
- Backend возвращал список и информацию о количестве результатов.
- При переходе между страницами выбранные фильтры сохранялись.
- Обрабатывались loading, error, empty и retry-сценарии.

**Моя зона ответственности:** frontend-логика фильтров, комбинирование параметров, интеграция с API, синхронизация URL и пагинация.

**Требует уточнения:** точные имена параметров API, структура ответа, правила кодирования параметров в URL и конкретные edge cases.

**Технические темы для подготовки:** серверная и клиентская фильтрация; URL как источник состояния; query-параметры; watch/computed; сброс page; согласованность фильтров и пагинации; обработка пустых результатов.

### 6.3. Авторизация и пользовательская сессия

**Сценарий:** вход в закрытую часть приложения по email и паролю.

**Моя frontend-зона ответственности:**
- форма входа;
- клиентская валидация обязательных полей и email;
- состояния загрузки и ошибки;
- предотвращение повторной отправки формы;
- вызов API и обработка результата;
- хранение пользовательского состояния в Pinia;
- защита навигации к закрытым маршрутам через Nuxt middleware;
- восстановление состояния при инициализации;
- обработка 401 и выхода пользователя.

**Согласованная модель сессии:**
- Backend поддерживал серверную сессию.
- Браузер получал HttpOnly cookie.
- В Pinia хранились ID пользователя, основные данные профиля и признак авторизации; пароль не сохранялся.
- При инициализации приложения выполнялась проверка сессии через API.
- При 401 пользовательское состояние очищалось, выполнялся переход на вход.
- Logout включал API-запрос и очистку локального состояния.
- Middleware ограничивал frontend-навигацию, но не заменял серверную проверку прав.

**Граница ответственности:** сервер создаёт и проверяет сессию и определяет доступ. Frontend отвечает за форму, отображение состояния, вызовы API и удобную навигацию. Нельзя утверждать, что middleware сам по себе обеспечивает безопасность закрытых данных.

**Требует уточнения:** точный API-контракт, способ восстановления сессии при SSR, cookie forwarding, имена полей ответа и конкретная схема logout.

**Технические темы для подготовки:** cookies; HttpOnly; Secure; SameSite; CSRF; XSS; 401/403; middleware; Pinia; восстановление сессии; различие UI-защиты и серверной авторизации.

## 7. Архитектурные и инженерные подходы

### 7.1. Компоненты и повторное использование

- Компоненты отвечают за отображение и пользовательские события.
- Данные передаются через props, события поднимаются через emits.
- Повторно используемая реактивная логика выносится в composables.
- Общие данные пользователя и авторизации находятся в Pinia.
- Локальное состояние интерфейса, например фильтры конкретной страницы, не переносится в глобальный store без необходимости.

Это описание принятых принципов; точные названия файлов и модулей не зафиксированы.

### 7.2. API и асинхронные состояния

Общий маршрут данных: действие пользователя → обработчик компонента → composable/service → HTTP-запрос → обработка ответа → состояние → обновлённый интерфейс.

Для значимых асинхронных сценариев предусматривались:
- loading;
- success;
- empty;
- error;
- retry там, где он уместен;
- защита от повторной отправки;
- отмена или игнорирование устаревших запросов там, где это важно.

Axios применялся как HTTP-клиент. Для запросов использовались соответствующие HTTP-методы GET, POST, PATCH и DELETE. Точные endpoint и контракты в этом документе не фиксируются.

### 7.3. TypeScript

TypeScript применялся для типизации:
- моделей вакансий и пользователя;
- параметров фильтров;
- API-ответов;
- props и событий компонентов;
- состояния и публичных интерфейсов composables.

Для дальнейшего технического разбора полезны interface/type, union types, generics, Partial, Pick, Omit и narrowing. Не утверждать, что TypeScript автоматически проверяет корректность runtime-ответа от backend.

### 7.4. Стили и адаптивность

- HTML5, CSS/SCSS.
- Scoped styles там, где это соответствовало компонентному подходу.
- Классы с подходом, близким к BEM.
- Flexbox и Grid.
- Адаптация под мобильные, планшетные и desktop-разрешения.
- Работа по макетам Figma.

### 7.5. Производительность

В рамках frontend-разработки использовались или рассматривались уместные практики:
- lazy loading отдельных страниц и тяжёлых компонентов;
- отложенная загрузка изображений;
- оптимизация изображений;
- code splitting;
- debounce для поиска;
- AbortController для отмены неактуальных запросов;
- серверная фильтрация и пагинация вместо загрузки всего набора данных;
- computed/watch и повторное использование компонентов;
- Chrome DevTools и Lighthouse для диагностики.

**Ограничение:** измеренные значения Core Web Vitals, проценты ускорения, исходные показатели и результаты экспериментов не зафиксированы. Не заявлять количественное улучшение производительности без измерений.
