# 2. Проект A — корпоративная экосистема промышленного предприятия «Купол»

**Заказчик:** Ижевский электромеханический завод «Купол».  
**Тип продукта:** корпоративный сайт, карьерное направление и сайты гражданской продукции.  
**Опубликованный срок основного корпоративного сайта:** 7 месяцев.  
**Период реконструкции:** 2023–2026; точные даты проекта публично не установлены.

## 2.1. Бизнес-контекст

Заказчику требовалось одновременно представлять предприятие как промышленного производителя и работодателя, развивать гражданское направление и упростить получение информации разными аудиториями.

Основные аудитории:

| Аудитория | Пользовательская задача |
|---|---|
| Соискатели | Изучить карьерные возможности и подразделения |
| Молодые специалисты | Найти информацию о программах обучения и трудоустройстве |
| B2B-заказчики | Изучить гражданскую продукцию и отправить запрос |
| Партнёры | Получить информацию о предприятии и направлениях деятельности |
| Пресс-служба | Управлять новостями и публикациями |
| Подразделения предприятия | Обновлять относящуюся к ним информацию |

По опубликованному кейсу, более 80% посетителей корпоративного сайта составляли потенциальные соискатели. Nutnet также проводила UX/UI-аудит и пересматривала информационную архитектуру, поскольку в исходных прототипах отсутствовали важные страницы подразделений.

## 2.2. Глобальная бизнес-техническая проблема

Главная задача — создать масштабируемую цифровую экосистему с разными пользовательскими сценариями и независимым управлением контентом, способную работать в контролируемой инфраструктуре предприятия.

Проблема состоит из нескольких взаимосвязанных частей:

1. Разные аудитории приходят на сайт с разными целями.
2. Информация принадлежит разным подразделениям и должна обновляться без участия разработчиков.
3. Одни и те же сущности могут отображаться на нескольких страницах.
4. Заказчик предъявляет ограничения к инфраструктуре и внешним зависимостям.
5. Корпоративный сайт и сайты гражданской продукции имеют разные бизнес-сценарии, но должны сохранять согласованный визуальный язык.

Nutnet публично указывает, что в ходе проекта пришлось менять согласованный стек из-за требований к отечественному ПО и инфраструктуре предприятия, включая переход серверной ОС на Astra Linux. После релиза первого сайта гражданской продукции также были отключены внешние запросы к сторонним сервисам Bitrix и АСПРО.

## 2.3. Диагностика

До выбора архитектуры необходимо исследовать четыре области.

**Пользовательские сценарии**
- определить, зачем посетители приходят на сайт;
- проверить путь соискателя от главной страницы до информации о вакансии или подразделении;
- изучить путь B2B-заказчика до запроса коммерческого предложения;
- выявить недостающие страницы и дублирование информации.

**Контентная модель**
- предприятие;
- подразделения;
- направления деятельности;
- продукция;
- новости и публикации;
- вакансии и карьерные программы;
- контакты и формы обращений.

**CMS и API**
- какие типы контента существуют;
- какие поля редактируются администраторами;
- как устроены права;
- какие данные доступны через API;
- как выполняется публикация и обновление материалов.

**Инфраструктура**
- разрешённые внешние соединения;
- наличие CDN и сторонних скриптов;
- способ доставки статических ресурсов;
- доступность API из SSR-окружения;
- требования к сборке и развёртыванию;
- возможность обновления приложения без обращения к внешним сервисам.

Результат — согласованная схема контента, список ограничений окружения и контракты между frontend и CMS.

## 2.4. Сравнение архитектурных вариантов

| Вариант | Преимущества | Ограничения |
|---|---|---|
| Полностью серверный сайт на CMS | Простая инфраструктура, единая система управления | Сильная связь frontend и backend, ограниченная гибкость интерфейса |
| SPA на Vue | Независимый интерфейс, удобная компонентная разработка | Нужно отдельно решать SEO и первоначальный рендеринг |
| Headless CMS + Nuxt SSR | Разделение контента и интерфейса, SEO, гибкость | Дополнительные требования к API и SSR-инфраструктуре |
| Отдельное приложение для каждого сайта | Независимое развитие | Дублирование компонентов и логики |

В опубликованном кейсе Nutnet действительно описывает разделение контента и frontend, Headless CMS и SSR. Для сайтов гражданской продукции использовалось готовое решение АСПРО.

Предлагаемое решение — использовать Nuxt SSR и отдельный API-контракт для контента, сохраняя самостоятельность сайтов гражданского направления.

## 2.6. Инфраструктурная проблема: SSR и отсутствие внешних зависимостей

В закрытом или контролируемом контуре приложение не должно зависеть от CDN, внешних шрифтов и сторонних скриптов для отображения основного контента.

Предлагаемые меры:

1. Включить необходимые зависимости в собственную сборку.
2. Размещать шрифты, изображения и статические ресурсы в контролируемом окружении.
3. Исключить внешние вызовы во время SSR.
4. Зафиксировать разрешённые API и домены.
5. Проверять production-сборку на неразрешённые внешние запросы.
6. Сделать необязательные интеграции некритичными для отображения страницы.

Для Nuxt SSR дополнительно проверять:
- одинаковые данные при серверном рендеринге и гидратации;
- отсутствие обращения к window/document на сервере;
- корректное использование useAsyncData;
- отсутствие повторных запросов после гидратации;
- обработку API-ошибок;
- работу динамических компонентов на клиенте.

Если аналитический или картографический сервис недоступен, основной контент должен оставаться доступным.

## 2.7. Сайты гражданской продукции

Nutnet указывает, что разработала три из четырёх сайтов гражданского направления: теплообменное оборудование, оборудование для атомных станций и химические решения. На сайтах предусмотрены оформление заказов для физических лиц и запросы коммерческих предложений для бизнеса. Использовалось готовое решение АСПРО.

Предлагаемая frontend-стратегия:
- общий слой дизайн-системы;
- повторно используемые карточки продукции;
- унифицированные формы;
- общие элементы навигации;

Не следует превращать карточку товара в компонент с десятками необязательных полей. Лучше иметь базовую модель и расширения по категориям.

# 3. Проект B — ELMA.Portal: корпоративный портал бизнес-процессов

**Тип продукта:** корпоративный B2B-портал.  
**Опубликованная продолжительность первоначального MVP:** 9 месяцев.  
**Тип задач:** веб-приложение, интеграция с BPM, динамические формы и ролевые сценарии.

## 3.1. Бизнес-контекст

ELMA.Portal предназначен для сотрудников, партнёров, поставщиков, дилеров и клиентов, которым требуется единый интерфейс для взаимодействия с бизнес-процессами.

Портал позволяет:
- запускать процессы;
- получать и выполнять задачи;
- отслеживать статусы;
- взаимодействовать с бизнес-процессами;
- расширять стандартную функциональность отдельными модулями.

Nutnet указывает интеграцию с ELMA BPM, возможность масштабирования и нагрузку до 1200 RPS на узел.

В опубликованном описании указаны Vue.js и Vuetify на frontend, Lumen, Redis, PostgreSQL и RabbitMQ на backend/инфраструктурной стороне.

## 3.2. Глобальная проблема: динамическая бизнес-логика не должна превращать frontend в набор отдельных страниц

Разные организации и роли используют разные процессы.

Примеры:

**Поставщик**
- регистрация;
- загрузка документов;
- проверка реквизитов;
- согласование договора;
- подтверждение доступа.

**Дилер**
- оформление заявки;
- согласование заказа;
- получение документов;
- отслеживание исполнения.

**Сотрудник**
- подача заявления;
- получение задачи;
- согласование;
- просмотр результата.

Если создавать отдельную страницу под каждый процесс, frontend будет постоянно разрастаться. Изменение процесса потребует изменения интерфейса и нового релиза.

Но полностью универсальный JSON-renderer также не подходит: он затрудняет сложную логику, UX и поддержку.

Задача — отделить описание процесса от визуального отображения, сохранив возможность специализированных интерфейсов.

## 3.3. Диагностика

После этого выделить общие сущности: список задач, карточка задачи, статус, форма, действия согласования и история операций.

## 3.6. Ключевая инженерная проблема: конкурентное изменение состояния задачи

Пользователь открыл задачу на согласование. В другой вкладке или другим сотрудником состояние задачи изменилось. Первый пользователь нажимает «Отправить», но действие уже недопустимо.

Если frontend самостоятельно меняет статус после нажатия кнопки, он может показать ложное успешное завершение.

### Решение

1. Сервер остаётся источником истины для статуса и допустимых переходов.
2. API возвращает версию сущности или маркер актуальности.
3. Критичные операции выполняются с проверкой версии, например через ETag/If-Match, если backend поддерживает такой контракт.
4. Конфликт обрабатывается отдельно: frontend получает актуальные данные, обновляет доступные действия и показывает уведомление.
5. Пользовательский ввод сохраняется только если это безопасно.
6. Для критичных бизнес-переходов не используется оптимистичное отображение окончательного статуса до ответа сервера.

Это предотвращает рассинхронизацию интерфейса с реальным состоянием бизнес-процесса.

## 3.7. Производительность и масштабирование

Показатель 1200 RPS на узел относится к опубликованной серверной характеристике, а не к производительности frontend.

- отмена устаревших запросов;

## 3.8. Почему решение оптимально

# 4. Проект C — Tasty Coffee: коммерческая платформа и интеграционные сервисы

**Заказчик:** Tasty Coffee.  
**Тип продукта:** оптовый сайт, интерактивные пользовательские сервисы и веб-сервис контроля качества.  
**Точные даты и длительность отдельных разработок публично не раскрыты.**

## 4.1. Бизнес-контекст

Tasty Coffee — производитель и поставщик свежеобжаренного кофе.

Nutnet описывает:
- обновление оптового сайта;
- интерактивную карту кофеен на Яндекс API;
- англоязычную версию;
- игры «Игра Вкуса» и «Победи колорсортер»;
- видеоотзывы оптовых клиентов;
- веб-сервис проверки качества кофе;
- базу данных и интеграции с 1С и Cropster.

## 4.2. Глобальная проблема: развитие цифровых каналов без замены действующей бизнес-инфраструктуры

У заказчика уже есть работающие системы продаж, управления контентом и производственного учёта. Новый frontend должен расширить пользовательские сценарии, не нарушив существующие процессы.

Разные источники данных имеют разные модели и правила обновления. Если браузер будет обращаться ко всем системам напрямую, frontend окажется связан с внутренними контрактами CMS, 1С и Cropster.

Задача — сохранить работающую платформу, постепенно выделяя новые пользовательские сервисы и нормализуя данные на серверной стороне.

## 4.3. Диагностика

Сначала определяются пользовательские потоки.

**Оптовый клиент**
1. Открывает оптовый сайт.
2. Изучает ассортимент.
3. Находит продукт.
4. Переходит к обращению или покупке.
5. Взаимодействует с действующей оптовой системой.

**Партнёрская кофейня**
1. Изучает программу сотрудничества.
2. Ищет точки на карте.
3. Открывает карточку кофейни.
4. Получает адрес и дополнительные сведения.

**Пользователь сервиса качества**
1. Открывает ссылку из QR-кода.
2. Передаёт идентификатор партии.
3. Получает результат проверки, если он доступен.

Последний сценарий — инженерная модель, основанная на публичном описании сервиса, QR-кода и интеграций; точный маршрут пользователя раскрыт не полностью.

Далее необходимо определить:
- владельца каждой сущности;
- источники данных;
- идентификаторы партий и товаров;
- частоту обновления;
- синхронные и асинхронные операции;
- правила обработки ошибок внешних систем.

## 4.4. Сравнение вариантов

| Вариант | Ограничения |
|---|---|
| Полностью переписать сайт и CMS | Высокая стоимость и риск для действующих продаж |
| Подключить все системы напрямую из браузера | Сильная связанность frontend и интеграций |
| Сохранить действующую платформу и выделять модули через API | Требуется API-слой, но ниже риск изменений |

Предпочтителен третий вариант. Публичный кейс указывает на сохранение действующей системы управления при обновлении frontend сайта.

## 4.5. Предлагаемая архитектура

```
Nuxt 3 / Vue 3
  ├── Wholesale site
  ├── Coffee map
  ├── Interactive applications
  ├── Quality service
  └── Localization
        |
        v
Integration API / BFF
  ├── CMS and wholesale system
  ├── 1C
  └── Cropster
```

BFF здесь — предлагаемая архитектура реконструкции, а не подтверждённая внутренняя реализация Nutnet.

## 4.6. Frontend-задача: не затрагивать работающую CMS

Основной сайт продолжает использовать действующую систему управления контентом. Новые интерактивные сервисы должны иметь собственные ограниченные области ответственности.

Предлагаемая структура:

```

  coffee-map/

    composables/
    services/
    types/

    components/
    composables/
    services/
    types/
  quality-service/
    components/
    services/
    types/
shared/
  ui/
  api/
  utils/
```

Это позволяет развивать карту или игру без переписывания каталога и основной части сайта.

## 4.7. Интерактивная карта на Яндекс API

Nutnet публично указывает использование Яндекс API для карты кофеен.

Frontend должен разделять:
- данные кофейни;
- состояние карты;
- состояние выбранной точки.

Модель точки содержит стабильный ID, название, адрес, координаты и дополнительные сведения.

Последовательность:
1. Загрузить точки через API.
2. Нормализовать координаты.
3. Отобразить маркеры.
4. Синхронизировать выбор маркера со списком.
5. Открыть карточку выбранной кофейни.
6. При большом количестве точек применить кластеризацию.
7. При недоступности картографического API показать список с адресами.

Карта не должна быть единственным способом получить контактную информацию.

## 4.8. Мультиязычность

Для англоязычной версии необходимо централизовать локализацию и маршрутизацию.

Примеры маршрутов:
- /wholesale/ и /en/wholesale/;
- /about/ и /en/about/;
- /coffee-map/ и /en/coffee-map/.

Проверяются:
- локализованные метаданные;
- canonical и hreflang;
- соответствие URL языку;
- fallback при отсутствии перевода;
- переключение языка на эквивалентную страницу.

Нельзя показывать пустую страницу или смешивать языки, если перевод ещё не подготовлен.

## 4.9. Сервис проверки качества кофе

Публичные материалы подтверждают создание базы данных и веб-сервиса проверки качества с интеграциями в 1С и Cropster.

Предлагаемый сценарий:
1. Пользователь открывает URL из QR-кода.
2. Frontend получает идентификатор партии.
3. Отправляет его в API сервиса.
4. Backend получает информацию из необходимых источников.
5. Нормализует результат.
6. Frontend отображает статус и доступные сведения.

Браузер не должен обращаться напрямую к 1С или Cropster: это связывает frontend с внутренними контрактами систем и переносит интеграционную логику в клиент.

Условная модель состояния:

```ts
type QualityStatus =
  | 'idle'
  | 'loading'
  | 'available'
  | 'not-found'
  | 'error'

interface CoffeeBatch {
  id: string
  batchNumber: string
  productName: string
  qualityStatus: QualityStatus
  checkedAt: string | null
}
```

Важно различать:
- not-found — партия не найдена;
- error — система не смогла получить результат;
- available — подтверждённый результат доступен.

Техническая ошибка не должна трактоваться как отрицательный результат проверки качества.

### Недоступность внешних систем

Если один источник временно не отвечает:
- backend применяет согласованные retry-политики;
- операция получает промежуточный статус;
- frontend сообщает, что результат пока недоступен;
- повторное получение результата не должно создавать дублирующую операцию;
- окончательное состояние определяется сервером.

## 4.10. Почему архитектура оптимальна

- ошибки внешних систем обрабатываются единообразно;
- англоязычная версия не требует дублирования приложения;
- новые пользовательские сценарии можно добавлять постепенно.
