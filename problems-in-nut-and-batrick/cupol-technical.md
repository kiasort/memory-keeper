# «Купол» — техническая реконструкция frontend-задачи

> **Статус документа:** инженерная реконструкция на основе постановки задачи, переданной для легенды Бадрик Лаб. Конкретный проект, состав команды, инциденты, сроки и личный вклад не подтверждены независимыми источниками. Документ описывает реалистичный способ решения задачи в рамках технологического контекста Бадрик Лаб 2021–2023 годов. Не следует выдавать модельные детали за подтверждённые события.

## 1. Краткое описание задачи

**Бизнес-проблема:** предприятие может менять операционные системы, серверную инфраструктуру и backend-реализации из-за внешних требований. При этом бизнес хочет сохранить пользовательские сценарии и не переписывать frontend при каждой смене инфраструктуры.

**Frontend-цель:** уменьшить связанность пользовательского приложения с конкретными адресами API, форматами ответов и деталями серверной реализации.

**Предлагаемое решение:** единый слой взаимодействия с API, внешняя конфигурация окружения, нормализация ответов и согласованный контракт с backend. Если серверные реализации отличаются, эти различия нужно скрыть за серверным API Gateway / BFF либо ограниченными адаптерами.

**Важно:** переход Windows → Astra Linux — не frontend-задача. Его выполняют инфраструктурные и системные специалисты. Frontend должен быть спроектирован так, чтобы не зависеть от ОС, на которой размещён backend.

## 2. Контекст и ограничения

### 2.1. Технологическая рамка

Для реконструкции используется стек, согласованный с общими технологическими рамками Бадрик Лаб на 2021–2023 годы:

- JavaScript ES6+;
- Vue 2 и Options API для существующего приложения;
- Vuex для общего состояния;
- Vue Router;
- Axios;
- HTML, SCSS;
- Webpack;
- jQuery может присутствовать в legacy-частях, но не должен участвовать в новом API-слое.

Конкретные версии библиотек и фактический стек самого проекта «Купол» не подтверждены. Не следует приписывать ему Vue 3, TypeScript, Nuxt или Pinia без отдельного подтверждения.

### 2.2. Что именно должно переживать смену инфраструктуры

С точки зрения frontend нужно изолировать:

1. Адрес backend и базовый URL API.
2. Детали маршрутизации запросов между разными серверными реализациями.
3. Форматы ответов, если они отличаются между версиями API.
4. Общую обработку сетевых ошибок.
5. Поведение авторизации и сессии в пределах согласованного клиент-серверного контракта.
6. Доступность интеграций в разных окружениях.
7. Конфигурацию сборки и развёртывания.

При этом бизнес-правила, хранение данных, маршрутизация к внутренним системам, интеграции с БД и взаимодействие с ОС остаются на стороне backend / инфраструктуры.

## 3. Как проявляется проблема в приложении

Предположим, корпоративное приложение состоит из каталога, личного кабинета, форм обращений и раздела новостей.

В исходной реализации могли встречаться такие зависимости:

- каталог самостоятельно содержит адрес API;
- профиль пользователя использует другой базовый URL;
- форма обращения формирует запрос по собственному контракту;
- разные компоненты по-разному обрабатывают сетевые ошибки;
- преобразование ответа сервера в формат для отображения выполняется непосредственно внутри компонентов;
- часть URL интеграций зафиксирована в исходном коде или в настройках сборки.

Если меняется адрес API или формат ответа, разработчику приходится исправлять несколько несвязанных компонентов. Это увеличивает объём повторной работы и повышает риск регрессий (поломок ранее работавшей функциональности).

## 4. Диагностика перед изменениями

Работу начинаем с инвентаризации интеграций. Нельзя просто заменить все URL одной строкой: сначала нужно понять, какие API используются и какие данные от них зависят.

### 4.1. Реестр интеграций

Для каждого пользовательского сценария фиксируем:

| Область | Что выяснить |
|---|---|
| Авторизация | URL, метод, формат ответа, cookie / token, истечение сессии |
| Профиль | Какие данные пользователя загружаются и обновляются |
| Каталог | Список методов, фильтры, пагинация, структура товара |
| Контент | Источник данных и формат страниц |
| Формы | Поля, обязательность, ошибки валидации, формат отправки |
| Статусы | Как клиент получает актуальное состояние операции |
| Файлы | Способ загрузки, допустимые форматы и ограничения |

Для каждого метода записываем владельца API, используемые компоненты, обязательные поля и поведение при ошибках.

### 4.2. Матрица окружений

Составляется таблица доступных окружений:

| Окружение | Frontend | API endpoint | Назначение |
|---|---|---|---|
| Local | Локальный запуск | Локальный proxy / dev API | Разработка |
| Development | Развёрнутая версия | Тестовый backend | Интеграция |
| Staging | Предрелизная версия | Предрелизный backend | Приёмка и регрессия |
| Production | Боевая версия | Боевой API | Работа пользователей |

Сами значения endpoint не должны быть рассыпаны по компонентам. Их должен определять единый механизм конфигурации.

### 4.3. Проверка различий между backend

С backend-разработчиками сравниваем контракты двух серверных конфигураций:

- совпадают ли маршруты;
- совпадают ли HTTP-методы;
- одинаковы ли типы полей;
- одинаково ли передаются пустые значения;
- совпадают ли коды ошибок;
- одинаково ли работает авторизация;
- одинаково ли обрабатываются пагинация и фильтры.

Если различия существенные, frontend не должен становиться универсальным переводчиком двух разных backend-систем. Предпочтительнее обеспечить единый внешний API-контракт на серверной стороне.

## 5. Архитектурное решение

### 5.1. Целевая схема

    Vue application
      |
      v
    API service layer
      |
      +-- apiClient
      +-- authService
      +-- catalogService
      +-- contentService
      +-- requestService
      |
      v
    Stable API endpoint
      |
      v
    API Gateway / BFF
      |
      +-- Backend implementation A
      |
      +-- Backend implementation B

Это целевая схема реконструкции. Наличие API Gateway или BFF в исходном проекте не подтверждено.

API Gateway (единая точка входа для запросов к нескольким серверным сервисам) или BFF (backend-for-frontend, серверный слой, адаптированный под потребности конкретного интерфейса) позволяет скрыть от frontend внутреннюю структуру серверных систем.

### 5.2. Один API-контракт вместо знания об ОС

Frontend не должен проверять, работает ли сервер на Windows или Astra Linux. ОС не является характеристикой пользовательского интерфейса.

Предпочтительный вариант:

- frontend всегда вызывает относительный адрес, например /api/v1;
- reverse proxy или API Gateway направляет запрос в нужную серверную реализацию;
- серверный адаптер приводит внутренние данные к общему контракту;
- backend возвращает единый формат ответа независимо от инфраструктуры.

Reverse proxy (промежуточный сервер, перенаправляющий запросы) и конфигурация маршрутизации относятся к инфраструктурной зоне ответственности.

Если организация не может обеспечить единый endpoint на стороне инфраструктуры, допускается runtime-конфигурация базового URL. Но это запасной вариант, а не причина хранить несколько адресов непосредственно в компонентах.

### 5.3. Единый HTTP-клиент

Создаётся один экземпляр Axios с общей конфигурацией:

    // apiClient.js
    import axios from 'axios'

    export const apiClient = axios.create({
      baseURL: window.APP_CONFIG.apiBaseUrl,
      timeout: 15000,
      withCredentials: true
    })

    apiClient.interceptors.response.use(
      response => response,
      error => Promise.reject(error)
    )

Это иллюстрация для браузерного Vue 2 SPA. Реальная конфигурация зависит от механизма авторизации и развёртывания.

Общий клиент отвечает за:

- базовый URL;
- таймауты;
- общие заголовки;
- передачу cookie, если используется cookie-based session;
- единое место подключения interceptors;
- унификацию сетевых ошибок.

Interceptor (перехватчик запросов или ответов) позволяет централизованно обработать общие технические сценарии, но бизнес-ошибки конкретной формы или операции должны оставаться явными.

### 5.4. Runtime-конфигурация

Чтобы не пересобирать приложение из-за каждого изменения адреса API, можно отдавать публичный конфигурационный файл рядом с frontend, например app-config.json:

    {
      "apiBaseUrl": "/api/v1",
      "environment": "production"
    }

При запуске приложение загружает конфигурацию до создания Vue-приложения. В ней нельзя хранить секреты, пароли, приватные ключи и серверные токены.

Если инфраструктура предоставляет стабильный относительный путь /api/v1, конфигурация может содержать только параметры, которые действительно отличаются между окружениями.

Это позволяет использовать один и тот же собранный frontend-артефакт для нескольких окружений, если это поддерживает принятый CI/CD-процесс.

### 5.5. Сервисный слой

Компоненты не должны сами знать маршруты API:

    // catalogService.js
    import { apiClient } from './apiClient'

    export const catalogService = {
      getProducts(params) {
        return apiClient.get('/catalog/products', { params })
      },

      getProduct(id) {
        return apiClient.get('/catalog/products/' + id)
      }
    }

    // ProductList.vue
    // Компонент обращается к catalogService, а не к Axios напрямую.

Сервисный слой отделяет транспортный код от интерфейса. Если меняется внешний API-контракт, правки локализуются в сервисах или адаптерах, а не распространяются по всем компонентам.

## 6. Нормализация данных и адаптеры

### 6.1. Зачем нужен адаптер

Разные backend-реализации могут возвращать одну сущность в разных форматах.

Вариант A:

    {
      "userId": 125,
      "fullName": "Иван Иванов"
    }

Вариант B:

    {
      "id": 125,
      "name": "Иван Иванов"
    }

Внутренний формат frontend:

    {
      "id": 125,
      "displayName": "Иван Иванов"
    }

Функция normalizeUser преобразует внешний объект к внутренней модели.

### 6.2. Где проходит граница адаптации

Адаптер на frontend уместен, если различия локальны и понятны: другое имя поля, формат даты, пустое значение или различающаяся структура вложенного объекта.

Если меняется бизнес-смысл, правила авторизации, жизненный цикл сущности или логика обработки операций, это нужно унифицировать на backend. Иначе frontend начнёт дублировать серверную бизнес-логику и станет зависеть от каждого варианта backend.

### 6.3. Единые модели и ошибки

Стоит согласовать единый формат ошибок:

- code — машинно-читаемый код;
- message — сообщение для пользователя или локализованный ключ;
- details — необязательные данные для отображения ошибок полей;
- traceId — идентификатор для поиска события в серверных логах.

Frontend отображает пользовательское сообщение, но не должен раскрывать стек-трейсы, внутренние адреса серверов и технические секреты.

## 7. Авторизация и сессии

Смена backend может затрагивать сессии, cookie и механизм авторизации. Поэтому до миграции необходимо согласовать:

- единый способ передачи credentials;
- путь и домен cookie;
- флаги Secure и SameSite, если используются cookie;
- поведение при истечении сессии;
- единый формат ошибки 401/403;
- сценарий повторного входа;
- правила выхода из системы.

Frontend сохраняет единый пользовательский сценарий: пользователь вошёл, получил профиль, работает с закрытыми разделами, а при окончании сессии получает понятное сообщение и направляется на авторизацию.

Нельзя пытаться решить различия в безопасности только клиентскими условиями.

## 8. Особенности смены окружений

### 8.1. CORS и сетевые настройки

CORS (Cross-Origin Resource Sharing — правила браузера для запросов между разными источниками) может отличаться между окружениями.

Предпочтительнее использовать единый origin и относительный API-путь через reverse proxy, если инфраструктура это позволяет. Если используются разные домены, backend должен корректно настроить разрешённые origin, методы, заголовки и credentials.

CORS нельзя исправить добавлением произвольного заголовка в браузерный запрос.

### 8.2. Сертификаты и доступность ресурсов

После переноса окружения нужно проверить:

- HTTPS и цепочку сертификатов;
- доступность API из браузера;
- DNS и сетевую маршрутизацию;
- cookie и домены;
- CSP (Content Security Policy — политику разрешённых источников ресурсов);
- доступность статических файлов;
- отсутствие зависимости от внешних ресурсов, запрещённых инфраструктурой.

Эти проверки выполняются вместе с DevOps и системными инженерами.

### 8.3. Сборка и развёртывание

Нужно разделить:
- build-time config — настройки, встраиваемые во время сборки;
- runtime config — настройки, читаемые приложением при запуске.

Если API endpoint зашит на этапе сборки, для другого окружения может потребоваться новая сборка. Runtime config позволяет избежать этого при корректной организации deployment.

## 9. Тестирование

### 9.1. Контрактные проверки

QA и backend-команда согласуют набор примеров ответов и ошибок. Frontend-сервисы проверяются на обоих вариантах окружения.

Contract testing (контрактное тестирование) подтверждает, что ожидаемые frontend поля и форматы соответствуют реальному API.

### 9.2. Матрица сценариев

| Сценарий | Проверка |
|---|---|
| Авторизация | Вход, выход, истечение сессии |
| Профиль | Корректность нормализованных данных |
| Каталог | Список, фильтры, пагинация, пустой ответ |
| Формы | Успешная отправка, ошибки полей, сетевой отказ |
| API недоступно | Таймаут и понятное сообщение |
| Переключение окружения | Те же сценарии на альтернативном backend |
| Данные различаются | Адаптер приводит ответ к общей модели |
| Статика | Все ресурсы загружаются в целевой инфраструктуре |

### 9.3. Регрессионное тестирование

После каждого этапа проверяются критичные пользовательские сценарии. Важно не допустить, чтобы перевод одного сервиса на новый API изменил поведение соседних разделов.

Перед выпуском на production фиксируются критерии отката:
- массовые ошибки API;
- невозможность авторизации;
- потеря или искажение данных;
- нарушение доступа;
- критические ошибки основных пользовательских сценариев.

## 10. План реализации и сроки

Оценка для ограниченного объёма работ:

| Этап | Плановая оценка |
|---|---:|
| Инвентаризация API и зависимостей | 3–5 рабочих дней |
| Согласование единого контракта | 3–5 рабочих дней |
| HTTP-клиент и runtime config | 4–7 рабочих дней |
| Перенос сервисов и адаптеров | 5–10 рабочих дней |
| Интеграционные и регрессионные проверки | 5–7 рабочих дней |
| Исправления и подготовка релиза | 3–5 рабочих дней |

**Оценка полного цикла: 6–8 календарных недель**, если backend и DevOps выполняют свою часть параллельно. Непосредственная frontend-разработка базового слоя может занять около 3–4 недель, а интеграционная проверка и устранение зависимостей — ещё часть общего срока.

Оценка не является исторически подтверждённой длительностью проекта.

## 11. Взаимодействие с командой

| Участник | Что согласовывается |
|---|---|
| Системный аналитик | Пользовательские сценарии, API-контракты, требования к совместимости |
| Backend-разработчики | Стабильные маршруты, DTO, формат ошибок, адаптеры серверов |
| DevOps / системные инженеры | Домены, proxy, конфигурации окружений, сборка и развёртывание |
| QA | Проверка интеграций, двух окружений и регрессии |
| Frontend-команда | HTTP-клиент, сервисы, адаптеры и поведение компонентов |
| Project Manager | Приоритеты, зависимости, этапы и критерии приёмки |

Работа разбивается на небольшие MR (Merge Request — запрос на включение изменений в общую кодовую базу). Каждый MR проходит code review (проверку кода другими разработчиками). Затем изменения проверяются на staging (предрелизном окружении), после приёмки выпускаются в production (боевую среду).

## 12. Ожидаемый бизнес-результат

Предлагаемая архитектура снижает связанность frontend с конкретной серверной реализацией.

При смене операционной системы или внутреннего backend frontend-компоненты не должны переписываться автоматически. Изменения локализуются в конфигурации, API Gateway / BFF и адаптерах серверных систем.

Бизнес получает:
- меньший объём повторной frontend-разработки;
- более предсказуемое переключение окружений;
- единое поведение интерфейса;
- локализованные изменения интеграций;
- понятную процедуру тестирования и отката.

## 13. Вариант рассказа для технического интервью

На проекте «Купол» была задача сделать frontend менее зависимым от меняющейся инфраструктуры предприятия. Заказчик мог менять серверные платформы и операционные системы, например переходить с Windows на Astra Linux, но хотел сохранить пользовательский интерфейс и не переписывать приложение при каждом изменении.

Я начал с анализа существующих интеграций: посмотрел, где используются адреса API, как устроены запросы, авторизация и обработка ответов. После этого предложил выделить единый слой взаимодействия с backend: общий Axios-клиент, сервисы для отдельных доменов и конфигурацию подключений отдельно от компонентов.

Также нужно было привести ответы разных серверных методов к единой внутренней модели. Для небольших отличий можно было использовать frontend-адаптеры, а существенные расхождения следовало скрыть за стабильным API-контрактом на серверной стороне.

Основная сложность заключалась в том, что некоторые интеграции были привязаны к старым адресам и форматам ответов. Дополнительно проверяли авторизацию, сетевые настройки и доступность ресурсов в разных окружениях.

Взаимодействие шло с аналитиком, backend-разработчиками, DevOps и QA. Изменения проходили code review, проверялись на staging и только после этого могли попадать в production.

В результате закладывалась архитектура, при которой основная часть frontend могла оставаться неизменной при переключении инфраструктуры.

## 14. Границы достоверности

### Исходная постановка задачи

В переданном описании задачи «Купол» указана проблема частых изменений стека и ОС, а также идея гибкого frontend, который позволяет переключать API/backend без перестройки самого сайта.

### Инженерная реконструкция

Не подтверждены историческими артефактами:
- наличие API Gateway или BFF;
- использование runtime config;
- конкретные Axios-сервисы и адаптеры;
- схема авторизации;
- реестр API и контрактные тесты;
- состав команды и сроки;
- конкретные инциденты и личный объём изменений.

Эти элементы показывают реалистичный путь решения поставленной задачи, но не являются доказательством фактически выполненной работы.

**Назначение:** техническая подготовка к собеседованиям и проработка инженерного решения. Перед использованием от первого лица необходимо подтвердить реальный личный вклад.
