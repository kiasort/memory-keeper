# Инженерные истории: «Купол» и Tasty Coffee

> **Статус документа:** техническая реконструкция и материал для подготовки к собеседованиям. Описанные архитектурные решения, сроки, сложности, состав команд и личный вклад являются моделью реалистичной коммерческой работы, а не подтверждёнными историческими фактами. Перед использованием рассказов как описания собственного опыта необходимо сверить их с реальными задачами и тем, что действительно выполнялось.

Документ объединяет две задачи:
- **Бадрик Лаб — «Купол»:** снижение зависимости frontend от конкретной реализации backend/API и инфраструктурного окружения.
- **Nutnet — Tasty Coffee:** универсальное отображение цен в разных валютах, ежедневное обновление курсов и поддержка нескольких рынков.

# 1. Бадрик Лаб — «Купол»: адаптация frontend к меняющейся инфраструктуре

**Тип продукта:** корпоративная цифровая экосистема промышленного предприятия.  
**Модельный период:** 2023 год.  
**Предполагаемый frontend-стек:** JavaScript, Vue 2, Vuex, Vue Router, Axios, HTML, SCSS, Webpack. Отдельные новые модули могли разрабатываться на Vue 3 после проверки совместимости.

## 1.1. Бизнес-контекст

Предприятие работает в условиях меняющихся требований к программному обеспечению и инфраструктуре. В зависимости от внешних обстоятельств может потребоваться использовать разные операционные системы, серверные конфигурации и программные платформы. Например, инфраструктура может переходить с Windows на Astra Linux или обратно.

Для бизнеса это создаёт риск: если frontend тесно связан с конкретной серверной реализацией, смена инфраструктуры может потребовать дополнительной адаптации интерфейса, API-интеграций и отдельных модулей приложения.

Заказчику требовалось не просто перенести сайт на другую операционную систему, а подготовить цифровую экосистему, которую можно адаптировать к изменениям инфраструктуры без постоянной переработки пользовательского интерфейса.

Важно разделять зоны ответственности: переход серверов с Windows на Astra Linux — задача инфраструктурной и backend-команд. Frontend-разработчик отвечает за то, чтобы приложение не зависело от особенностей конкретной серверной реализации.

## 1.2. В чём заключалась проблема

Проблема находилась не в визуальной части сайта, а в архитектурных связях между frontend, API и серверными системами.

В традиционной реализации отдельные компоненты могут напрямую зависеть от конкретных адресов API и форматов ответов:
- страница каталога самостоятельно обращается к одному API;
- личный кабинет использует другой адрес backend;
- форма отправки заявок зависит от отдельного серверного метода;
- настройки интеграций могут быть зашиты непосредственно в исходный код;
- компоненты самостоятельно преобразуют ответы серверов и обрабатывают ошибки.

При замене серверного приложения или изменении структуры API разработчикам приходится искать все места, где используется старый контракт, и исправлять их по отдельности.

**Бизнес-цель:** сохранить внешний пользовательский интерфейс и основные сценарии при замене или перенастройке серверной инфраструктуры.

## 1.3. Анализ существующих интеграций

Работу следует начинать с аудита, а не с переписывания компонентов.

Совместно с аналитиком и backend-разработчиком составляется перечень интеграций:
1. Авторизация и получение информации о пользователе.
2. Загрузка корпоративного контента.
3. Работа с каталогом.
4. Получение справочников и классификаторов.
5. Отправка заявок и форм.
6. Получение статусов и результатов операций.

Для каждой интеграции проверяются:
- используемый адрес API;
- HTTP-методы и параметры запросов;
- формат ответа и обязательные поля;
- правила авторизации;
- коды ошибок;
- поведение при недоступности сервера;
- зависимости от конкретного окружения.

Результатом анализа становится список мест, в которых frontend зависит от конкретного API, и перечень контрактов, которые необходимо стабилизировать.

## 1.4. Основное решение — единый API-слой

Вместо прямых обращений к серверным адресам из Vue-компонентов выделяется отдельный сервисный слой — часть приложения, которая отвечает за взаимодействие с API.

Примерная структура:

```text
src/
  components/
    catalog/
    forms/
    profile/

  services/
    api/
      apiClient.js
      authService.js
      catalogService.js
      contentService.js
      requestService.js

  adapters/
    normalizeUser.js
    normalizeProduct.js
    normalizeRequest.js

  store/
    modules/
      auth.js
      catalog.js

  config/
    runtimeConfig.js

  views/
```

### Единый HTTP-клиент

Axios используется через общий экземпляр `apiClient`, а не создаётся независимо в каждом компоненте.

HTTP-клиент (модуль, который отправляет запросы и обрабатывает ответы сервера) получает общую конфигурацию при запуске приложения. В нём централизуются базовый URL, общие заголовки, обработка сетевых ошибок и, при необходимости, механизмы авторизации.

### Runtime-конфигурация

Адреса API выносятся из компонентов и бизнес-логики в runtime config (конфигурацию, доступную приложению при запуске, а не жёстко зафиксированную в исходном коде).

Условный пример:

```json
{
  "apiBaseUrl": "/api/v1",
  "environment": "production"
}
```

Это иллюстрация, а не реальная конфигурация проекта. При развёртывании приложения на другом окружении DevOps (специалист, отвечающий за сборку, окружения и развёртывание) или ответственный за конфигурацию инженер меняет настройки подключения. Сам frontend-код при этом не требуется переписывать.

В конфигурации не должны храниться секреты, пароли или закрытые токены.

### Адаптеры данных

Разные backend-реализации могут возвращать одну и ту же сущность в разных форматах.

Например, один API:

```json
{
  "userId": 125,
  "fullName": "Иван Иванов"
}
```

Другой API:

```json
{
  "id": 125,
  "name": "Иван Иванов"
}
```

Компонентам не нужно знать об этих различиях. Адаптер (функция преобразования данных на границе интеграции) приводит ответы к единой внутренней модели. Например, `normalizeUser` возвращает объект с согласованными полями пользователя независимо от источника данных.

### Стабильный контракт API

С backend-командой согласовывается стабильный внешний контракт: маршруты, методы, форматы запросов и ответов, обязательные поля и правила ошибок.

Если серверные реализации различаются, предпочтительно обрабатывать это на стороне backend через API Gateway или адаптеры (промежуточный слой, который маршрутизирует запросы и при необходимости преобразует данные).

Frontend не должен самостоятельно определять, какая операционная система установлена на сервере, и переключать бизнес-логику в каждом компоненте.

## 1.5. Предлагаемая схема взаимодействия

```text
Vue frontend
  |
  v
Единый API-слой
  |-- Axios HTTP-клиент
  |-- сервисы
  |-- адаптеры данных
  |-- внутренние модели
  |
  v
API Gateway / backend adapter
  |
  +--> Среда Windows
  |
  +--> Среда Astra Linux
```

Это предлагаемая архитектура, а не подтверждённая схема реальной инфраструктуры предприятия.

## 1.6. Сложности по ходу реализации

**1. Разные форматы ответов API.**  
В ходе проверки интеграций могут обнаружиться различия в названиях полей, типах значений и обработке пустых ответов.

Решение: согласовать единые DTO (структуры данных, которыми обмениваются клиент и сервер), а временные несовпадения обрабатывать адаптерами на границе сервисного слоя.

**2. Жёстко заданные адреса API.**  
Некоторые запросы могут использовать URL, которые нельзя централизованно переключить.

Решение: постепенно перевести запросы на общий HTTP-клиент и вынести адреса в конфигурацию.

**3. Различия в авторизации.**  
При смене backend могут отличаться механизмы работы с сессиями, cookie (небольшие данные, которые браузер хранит и отправляет серверу) и обработкой ошибок авторизации.

Решение: совместно с backend-командой согласовать единый сценарий входа, получения пользователя, завершения сессии и обработки её истечения. Frontend сохраняет одинаковое пользовательское поведение, а серверная сторона обеспечивает совместимый контракт.

**4. Особенности инфраструктуры.**  
На новой среде могут отличаться сетевые настройки, CORS (правила браузера, ограничивающие запросы между разными источниками), сертификаты и доступность ресурсов.

Решение: совместно с DevOps и системными инженерами проверить конфигурацию окружения. Такие ограничения нельзя устранить только изменением Vue-компонентов.

**5. Регрессионные ошибки при переключении окружения.**  
Интерфейс может работать в старой среде и ломаться после переключения backend.

Решение: проверять одни и те же пользовательские сценарии на обеих конфигурациях, а не ограничиваться локальным запуском.

## 1.7. Взаимодействие с командой

| Участник | Зона согласования |
|---|---|
| Системный аналитик | Пользовательские сценарии, API-контракты, требования к совместимости |
| Backend-разработчики | Единая структура ответов, API Gateway, адаптеры серверных систем |
| DevOps / системные инженеры | Конфигурации окружений, сборки и развёртывания |
| QA | Проверки на обеих инфраструктурах, регрессионные сценарии |
| Frontend-разработчики | HTTP-клиент, сервисы, адаптеры и поведение компонентов |
| Project Manager | Приоритеты, зависимости и последовательность работ |

Работу можно разделить на небольшие MR (Merge Request — запрос на включение изменений в общую кодовую базу). Изменения проходят code review (проверку кода другими разработчиками), затем проверяются на staging (тестовом предпроизводственном окружении). После приёмки и согласования релиза изменения попадают в production (боевую среду, доступную пользователям).

Оценка для такой задачи:

| Этап | Оценка |

Это плановая оценка для реконструированного сценария, не опубликованный срок проекта.

## 1.9. Ожидаемый результат

Предприятие получает frontend, менее зависимый от конкретной серверной реализации. При изменении операционной системы, серверной конфигурации или внутренней реализации backend не требуется автоматически переписывать пользовательские компоненты.

Изменения локализуются в конфигурации, API-интеграционном слое и серверных адаптерах. Для бизнеса это означает потенциальное снижение стоимости сопровождения и более предсказуемое переключение между инфраструктурными конфигурациями.

# 2. Nutnet — Tasty Coffee: единое отображение цен в разных валютах

**Тип продукта:** коммерческая платформа и оптовый сайт.  
**Модельный стек:** Vue/Nuxt; точные версии для проекта публично не раскрыты.  
**Статус валютной задачи:** инженерная реконструкция на основе отдельной постановки задачи; публичное подтверждение реализации именно такого валютного модуля отсутствует.

## 2.1. Бизнес-контекст

Tasty Coffee работает с разными рынками и использует российские рубли и американские доллары. При дальнейшем расширении международного присутствия необходимо поддерживать дополнительные валюты и учитывать особенности локальных рынков.

Проблема заключается не только в переводе цены из одной валюты в другую. Цена товара для российского рынка и цена того же товара для американского рынка могут отличаться не только из-за обменного курса, но и из-за логистики, налогов и коммерческой политики.

**Бизнес-задача:** создать универсальный механизм отображения цен, который позволит переключать валюты, ежедневно получать актуальные обменные курсы и постепенно подключать новые рынки без разработки отдельных frontend-компонентов для каждой страны.

## 2.2. Разделение языка, валюты и рынка

На старте необходимо разделить три понятия:

1. **Язык интерфейса** — русский, английский и другие языки.
2. **Валюта отображения** — RUB, USD, KZT, UZS и другие.
3. **Коммерческий рынок** — страна или регион, для которого действуют определённые цены и правила продаж.

Эти настройки нельзя считать одним параметром. Например, англоязычный пользователь может покупать продукцию на российском рынке в рублях.

Валюта отвечает за представление суммы, а коммерческий рынок — за применяемые цены и условия продажи.

## 2.3. Два режима ценообразования

Для коммерческого сайта недостаточно обычного конвертера, который умножает любую цену на текущий курс. Предлагается предусмотреть два режима.

### Фиксированная цена для рынка

Для конкретного рынка действует отдельный прайс-лист:
- российский рынок — цена в RUB;
- американский рынок — цена в USD.

Такие цены определяются коммерческими правилами компании и не обязаны ежедневно изменяться вслед за обменным курсом.

### Автоматическая конвертация

Если для конкретного рынка нет отдельного прайс-листа, система может пересчитать базовую цену по утверждённому курсу.

Например:
- базовая цена товара — 100 USD;
- утверждённый курс — 80 RUB за 1 USD;
- отображаемая цена — 8000 RUB.

Курс условный. Автоматическую конвертацию следует использовать только там, где это разрешено бизнес-правилами. Приоритет должна иметь утверждённая локальная цена.

## 2.4. Архитектура получения валютных курсов

Ответственность frontend и backend необходимо разделить.

На серверной стороне предлагается отдельный валютный сервис, который:
1. Получает курсы у внешнего поставщика данных.
2. Проверяет корректность полученного ответа.
3. Сохраняет курсы в собственной базе данных.
4. Предоставляет их frontend через внутреннее API.
5. Хранит время последнего успешного обновления.
6. Обеспечивает резервный сценарий при недоступности внешнего источника.

Обновление запланировано один раз в сутки — в 00:00 UTC (всемирное координированное время).

Для этого backend-разработчик настраивает Cron Job (запланированную серверную задачу, выполняющуюся по расписанию).

Не следует получать курсы непосредственно из браузера:
- внешний API может быть недоступен;
- у него могут быть ограничения по количеству запросов;
- разные пользователи могут получить разные значения в течение дня;
- нельзя доверять браузеру при расчёте окончательной коммерческой стоимости заказа.

Frontend получает уже подготовленные и сохранённые данные из API компании.

Условный ответ API:

```json
{
  "baseCurrency": "USD",
  "rates": {
    "USD": 1,
    "RUB": 80
  },
  "updatedAt": "2026-11-23T00:00:00Z"
}
```

Это иллюстрация контракта, не реальная схема API Tasty Coffee.

## 2.5. Frontend-реализация

Предлагается выделить три основные зоны.

### Универсальный компонент отображения цены

Вместо отдельных компонентов для каждой валюты создаётся один `ProductPrice`. Он принимает стоимость, код валюты и локаль форматирования.

Пример для Vue:

```vue
<template>
  <span>{{ formattedPrice }}</span>
</template>

<script>
export default {
  props: {
    amount: {
      type: Number,
      required: true
    },
    currency: {
      type: String,
      required: true
    },
    locale: {
      type: String,
      default: 'ru-RU'
    }
  },

  computed: {
    formattedPrice() {
      return new Intl.NumberFormat(this.locale, {
        style: 'currency',
        currency: this.currency
      }).format(this.amount)
    }
  }
}
</script>
```

Используется `Intl.NumberFormat` — встроенный механизм JavaScript для форматирования денежных значений с учётом локали и валюты.

Благодаря этому не нужно создавать отдельные компоненты для рублей, долларов, тенге или сумов.

### Сервис валют

В существующей архитектуре Vue/Nuxt можно выделить `currencyService`, который отвечает за получение валютных настроек и курсов.

Пример структуры:

```text
services/
  api/
    apiClient.js

  currency/
    currencyService.js
    currencyFormatter.js

  pricing/
    pricingService.js

components/
  pricing/
    ProductPrice.vue
    CurrencySelector.vue

composables/
  useCurrency.js
```

Общее состояние валют хранится в принятом в проекте state manager (механизме управления состоянием приложения), например Vuex или Pinia, в зависимости от фактической версии Vue и архитектуры проекта.

В нём находятся:
- выбранная валюта;
- локаль;
- доступные валюты;
- время последнего обновления курса;
- состояние загрузки.

Окончательное значение коммерческой цены и правила её расчёта определяются backend, а не размазываются по frontend-компонентам.

### Универсальный переключатель валюты

При переключении RUB на USD пользователь должен видеть обновлённые цены во всех необходимых местах сайта.

Выбранная валюта становится общим состоянием приложения. Компоненты получают её из общего store и отображают значения в согласованном формате.

Переключение валюты не должно требовать перезагрузки всех страниц или создания новых компонентов.

## 2.6. Поддержка новых рынков и валют

При выходе на новые рынки выбранный поставщик курсов может не поддерживать все необходимые валюты.

Например:
- USD поддерживается;
- RUB поддерживается;
- KZT поддерживается;
- UZS отсутствует в API выбранного поставщика.

Нельзя передать неподдерживаемую валюту в конвертер и ожидать корректного результата.

Предлагаемые сценарии:

| Ситуация | Поведение системы |
|---|---|
| Валюта поддерживается основным API | Используется ежедневный курс |
| Основной поставщик временно недоступен | Используется последний подтверждённый курс с указанием времени либо резервный источник |
| Валюта не поддерживается поставщиком | Подключается альтернативный источник или согласованный коммерческий курс |
| Нет достоверного курса и локальной цены | Не показывается фиктивная стоимость; предлагается запросить цену |

Для Узбекистана, например, можно использовать отдельный утверждённый коммерческий курс или дополнительного поставщика данных. Конкретный источник должен согласовываться бизнесом и backend-командой.

Frontend отвечает за корректное отображение доступных валют, состояний загрузки и ошибок, но не должен самостоятельно придумывать отсутствующие значения.

## 2.7. Региональные ограничения и защита от злоупотреблений

Отдельное бизнес-требование касается ситуации, когда пользователь меняет регион через VPN (технологию создания сетевого подключения через удалённый сервер), чтобы получить цены другого рынка.

Например, пользователь находится в России, но переключает регион на США и пытается воспользоваться американскими ценами.

Frontend не может надёжно определить реальное местонахождение человека: пользователь может использовать VPN, прокси, отключить геолокацию или изменить настройки браузера.

Поэтому предлагается разделить ответственность.

**Frontend:**
- предоставляет выбор доступной валюты;
- показывает рекомендованный регион;
- сохраняет пользовательские настройки;
- отображает цены согласно рынку, полученному от сервера;
- не считает само использование VPN доказательством нарушения.

**Backend:**
- определяет предполагаемую страну по IP;
- учитывает страну доставки и данные учётной записи;
- применяет правила доступности прайс-листов;
- повторно проверяет стоимость при оформлении заказа.

Определение страны по IP — лишь один из сигналов: VPN, прокси и мобильные сети могут давать неверный результат.

Главный принцип: переключение валюты и переключение коммерческого рынка — разные действия. Окончательное решение о применяемой цене принимает сервер.

## 2.8. Этапы реализации

**Этап 1. Анализ требований и коммерческих правил**

Совместно с аналитиком и менеджером определяются:
- валюты первоначального релиза;
- базовая валюта;
- рынки с фиксированными ценами;
- рынки, где разрешена автоматическая конвертация;
- правила определения региона;
- время и периодичность обновления курса.

**Этап 2. Backend-интеграция**

Backend-разработчики реализуют получение курсов, хранение значений и расписание обновления. Параллельно согласуется API-контракт, чтобы frontend получал данные в предсказуемом формате.

**Этап 3. Frontend-разработка**

Frontend-часть включает:
- универсальный компонент цены;
- переключатель валюты;
- интеграцию с валютным API;
- общее состояние валют;
- форматирование значений;
- синхронизацию валюты между страницами;
- обработку загрузки и ошибок.

**Этап 4. Региональная логика**

Проверяются настройки рынков, поведение при разных валютах и локалях, а также отображение цены для каждого региона.

**Этап 5. Интеграционное тестирование и релиз**

Проверяется весь путь от получения валютных данных до отображения цены и создания заказа.

## 2.9. Сложности по ходу реализации

**1. Курс обновился не вовремя.**  
Внешний поставщик может задержать ответ. Нельзя затирать последнюю корректную запись невалидными данными. Следует отображать время последнего успешного обновления и согласованный статус актуальности.

**2. Различия в правилах округления.**  
Например, 99,99 USD при условном курсе 80 RUB даёт 7999,20 RUB. Карточка товара, корзина и итог заказа не должны показывать разные суммы из-за независимого округления. Правила округления необходимо согласовать с backend и использовать единую серверную цену.

**3. Разные локали и валюты.**  
Проверяются английский интерфейс с рублями, русский интерфейс с долларами и единообразное отображение цен на разных страницах. Язык не должен автоматически определять коммерческий рынок.

**4. Расширение списка валют.**  
Нельзя добавлять условия вроде `if currency === 'RUB'` во все компоненты. Для этого и нужны единый формат данных, универсальное форматирование и конфигурация доступных валют.

**5. SSR в Nuxt.**  
При SSR (Server-Side Rendering — формировании HTML страницы на сервере) первоначальная валюта должна быть определена до отправки HTML пользователю. Иначе может возникнуть hydration mismatch (несовпадение HTML, сформированного сервером, с результатом клиентского рендеринга): сервер показал цену в долларах, а браузер сразу после загрузки переключил её на рубли.

Чтобы избежать такого поведения, выбранный рынок и валюта должны поступать из согласованной конфигурации пользователя до рендеринга страницы.

## 2.10. Взаимодействие с командой

| Участник | Зона согласования |
|---|---|
| Product Manager / бизнес-заказчик | Правила ценообразования, рынки, приоритеты |
| Аналитик | Пользовательские сценарии, требования к регионам, API-контракты |
| Backend-разработчик | Получение курсов, база данных, расписание обновления, расчёт коммерческих цен |
| Frontend-разработчик | Компоненты цен, состояние валют, API-интеграция |
| QA | Проверка валют, регионов, округления и сценариев ошибок |
| DevOps | Конфигурация окружений и работоспособность запланированных задач |

Ключевой формат взаимодействия — регулярная синхронизация с backend-разработчиком по контракту валютного API. Frontend и backend должны одинаково трактовать валюту, рынок, источник курса и время его актуальности.

После реализации отдельных модулей создаются MR, проводится code review и запускаются проверки на staging.

## 2.12. Ожидаемый результат

Компания получает единый механизм отображения цен, который:
- поддерживает несколько валют;
- позволяет переключать валюту без дублирования компонентов;
- получает курсы из централизованного источника;
- использует ежедневное обновление в 00:00 UTC;
- учитывает локальные цены разных рынков;
- предусматривает расширение на новые страны;
- корректно обрабатывает неподдерживаемые валюты;
- отделяет язык интерфейса от коммерческого региона.

Для бизнеса это создаёт основу международного масштабирования без необходимости создавать отдельную frontend-версию для каждой страны.

# 3. Краткие версии для собеседования

Эти версии предназначены для устного рассказа. Они намеренно короче технических разделов: на HR-скрининге важнее понятно объяснить бизнес-задачу, свою роль, взаимодействие с командой и результат, а технические детали раскрывать уже на техническом интервью.

## 3.1. «Купол» — версия для HR

На проекте «Купол» была задача сделать frontend более независимым от серверной инфраструктуры предприятия. У заказчика могли меняться серверные платформы и операционные системы, например происходил переход с Windows на Astra Linux. При этом бизнес хотел сохранить существующий пользовательский интерфейс и не переписывать его при каждом изменении инфраструктуры.

Я занимался frontend-частью этой задачи: анализировал существующие API-интеграции, выделял общий слой взаимодействия с backend, выносил настройки подключений из компонентов и приводил ответы разных серверных методов к единому формату.

Основная сложность заключалась в том, что часть компонентов была тесно связана с конкретными адресами API и форматами данных. Поэтому приходилось постепенно отделять интеграционную логику от интерфейса и согласовывать контракты с backend-разработчиками.

Работал совместно с аналитиком, backend-командой, DevOps и QA. Изменения проходили код-ревью и проверялись на тестовом окружении до выпуска в production.

В результате закладывалась архитектура, при которой смена серверной реализации не должна была приводить к массовой переработке frontend-компонентов. Для бизнеса это означало более удобное сопровождение и меньшую зависимость от конкретной инфраструктуры.

## 3.2. Tasty Coffee — версия для HR

На проекте Tasty Coffee была задача подготовить коммерческий сайт к работе с несколькими валютами и расширению на международные рынки.

Изначально компания использовала рубли и доллары, но при выходе на новые страны возникала проблема: не все валюты поддерживались одним поставщиком обменных курсов. Кроме того, цена на разных рынках могла отличаться не только из-за курса, но и из-за коммерческих условий.

Моя frontend-зона заключалась в том, чтобы сделать универсальное отображение цен: разработать общий компонент цены, переключение валюты, интеграцию с API курсов и единое состояние валют в приложении. Это позволяло не создавать отдельные компоненты под каждую страну.

С backend-командой согласовывали получение курсов и их ежедневное обновление в 00:00 UTC. Отдельно прорабатывали разделение языка, валюты и коммерческого региона, поскольку, например, смена языка не должна автоматически менять рынок и цену товара.

Из сложностей можно выделить округление, обработку отсутствующих курсов, синхронизацию валюты между страницами и первоначальную загрузку данных в Nuxt.

Работал совместно с аналитиком, backend-разработчиками и QA: согласовывали API-контракты, проверяли разные валюты и региональные сценарии, проводили код-ревью и тестирование перед релизом.

В результате получался единый механизм, который позволял расширять поддержку валют и рынков без дублирования frontend-логики.

## 5. Границы реконструкции

### Инженерные решения, представленные как предложения

- Единый API-слой и runtime config для «Купола».
- Адаптеры данных и стабильные DTO.
- API Gateway или backend adapters для изоляции серверных реализаций.
- Валютный сервис и ежедневная задача обновления курсов.
- Универсальный компонент цены и общее состояние валют.
- Резервный источник курса и обработка неподдерживаемых валют.
- Разделение валюты отображения и коммерческого рынка.
- Серверная проверка региональных цен и стоимости заказа.

### Что требует отдельного подтверждения перед использованием как личного опыта

- Фактические даты выполнения задач и продолжительность этапов.
- Конкретный состав команды и распределение ролей.
- Использование указанных технологий именно в этих проектах.
- Реальные инциденты и последовательность их устранения.
- Личный объём реализованного кода и принятых решений.
- Фактические результаты и бизнес-метрики.

**Назначение документа:** техническая подготовка и структурирование двух инженерных историй. Краткие версии для HR следует адаптировать под фактический личный вклад, а не представлять модельные детали как подтверждённые события.
